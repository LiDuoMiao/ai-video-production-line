# 环境检查报告编写规范

## 一、用途

在 02 阶段记录本期实际使用的共用环境、已执行的检查及结论，供后续阶段查找工具、配置和资源。报告存入本期工程，环境由工作区内各项目共用。

## 二、内容与格式

文件名为 `环境检查报告.md`，保存在本期工程的 `02 环境检查/`。将模板中的占位内容换成实际检查结果。

```markdown
# 环境检查报告

- 本期选题：<已确认的选题名称>
- 检查日期：<实际检查日期>
- 系统与架构：<实际运行系统和架构>
- 工作区：<实际工作区路径>
- 本期工程：<实际工程路径>
- 共用 Python 环境：<复用、新建或不适用，注明实际解释器路径和版本>

## 检查结果

| 检查项 | 实际路径、版本或配置 | 检查方法与结果 | 缺项处理与复查 |
| --- | --- | --- | --- |
| <检查项> | <实际取得的信息> | <执行的检查和判定> | <处理及复查结果，无则写「无」> |

## 结论

<就绪或阻塞。阻塞时写明缺项、所需条件及受影响环节。列出待后续核对的事项及负责阶段。>
```

## 三、字段和表格列怎么写

| 字段或列 | 填写要求 |
| --- | --- |
| 基本信息 | 填写本期选题、检查日期、系统和实际目录。共用环境写清是复用还是本次新建，并给出实际解释器路径和版本。 |
| 检查项 | 按本期需要记录目录权限、解释器及依赖、媒体工具、字体和资源、服务与查看工具等。 |
| 实际路径、版本或配置 | 写能供下游定位的实际路径、版本或工具入口。涉及凭据时记录配置状态即可。 |
| 检查方法与结果 | 写清做了什么、观察到什么，按实际情况写「通过」「待补齐」「阻塞」「不适用」或「待后续核对」。 |
| 缺项处理与复查 | 写明采取的动作、复查了哪些项及结果。仍缺的条件单独写清。 |
| 结论 | 02 范围内的必需项均通过时写「就绪」。仍有本阶段必需项无法完成时写「阻塞」，给出可接续的具体信息。「待后续核对」注明负责阶段，不影响 02 就绪。 |

## 四、自查与交接

核对报告的工程路径与实际目录一致。复用或新建的环境可定位，检查结果有实际依据，缺项和复查结论可追溯。配置检查和实际服务调用的结果分别记录。报告就绪后交 03 使用。
